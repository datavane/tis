# Ontology Workshop 自动化测试闭环方案

> 状态：设计草案 · 2026-10-25
> 关联：`ontology-workshop-test-strategy.md`（测试策略：测什么 / 分层金字塔）
> 本文档回答：**怎么跑、发现问题后怎么分析、怎么汇报、怎么回归**（运行态闭环）

---

## 1. 定位：测试不是一次性活动，而是一个持续闭环

静态的测试策略文档回答「测什么」，但真正让测试**可持续、可向用户交付可靠产品**的是
一个运行态的闭环：

```
┌──────────────────────────────────────────────────────┐
│  1. 执行    跑契约测试 + 前端 AOT（一条命令/skill 触发）   │
└────────────────────────┬─────────────────────────────┘
                         ▼ 发现失败
┌──────────────────────────────────────────────────────┐
│  2. 分析    AI 读失败日志 → 定位测试类 → 读相关源码       │
│             归类：契约坏 / 测试过期 / 环境问题            │
└────────────────────────┬─────────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────────┐
│  3. 汇报    结构化输出：根因 + 影响面 + 修复方向 + 归属     │
└────────────────────────┬─────────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────────┐
│  4. 修复    开发者（人）按汇报做决策、修复                │
└────────────────────────┬─────────────────────────────┘
                         ▼
┌──────────────────────────────────────────────────────┐
│  5. 回归    重跑同一批测试，确认转绿，再进下一次循环        │
└──────────────────────────────────────────────────────┘
```

**AI 在闭环中的角色是「测试分析员」**，不是「修复者」：
- AI 负责：跑测试、定位、分类、提炼关键点、给出修复方向。
- 开发者负责：决策（改产品代码还是改测试）、修复。
- 人机边界清晰：AI 不做无法回溯的代码改动，只做可复现的分析与汇报。

---

## 2. 分析阶段的决策树（闭环的核心价值）

测试失败后，AI 的第一个任务是**把失败归类**，因为三类失败的修复方向完全不同。
这是「简单分析问题、汇报关键点」的具体含义：

| 失败类型 | 典型特征 | 根因 | 修复方向 | 修复人 |
|---|---|---|---|---|
| **契约真坏** | 断言失败，且期望值/后端代码/前端代码三方中确有一方真的改了 | 前后端字段、枚举、`{impl,vals}` 线格式改了没同步 | 同步改另一边 | 开发者 |
| **测试过期** | 期望值硬编码在测试里，但产品演进使合法值变了 | 测试里登记的 token / 字段名 / 字面量过期 | 更新测试期望 | 开发者 |
| **环境问题** | `Assume` 跳过 / `ClassNotFound` / sezpoz 索引缺失 / `InaccessibleObjectException` | 前端工程缺席、`--add-opens` 缺失、注解处理器未跑 | 修环境 | 开发者或 AI |

**区分「契约坏」和「测试过期」是分析的关键**：前者改产品代码，后者改测试。
判错了会「为了绿而改测试」，掩盖真 bug——这正是 AI 分析要防的陷阱。

### 判断依据（AI 分析时按此顺序取证）

1. 读断言失败信息 → 提取「期望值」和「实际值」。
2. 读该测试类的契约登记处（如 `FRONTEND_EVENT_TYPES`、`ROW_EDITOR_FIELDS`、`BASES` 这些硬编码清单）。
3. 读对应产品代码（后端 `@FormField` / 前端 config 接口 / 枚举）。
4. 判定：**产品代码的演进是有意的（→ 测试过期），还是遗漏了同步（→ 契约坏）**。
   - 证据：git log / 最近改动该文件的 commit。
   - 无法判定时，如实汇报「无法判定，需开发者确认意图」，而不是擅自下结论。

## 3. 汇报模板（结构化，可直接给开发者看）

每次回归发现失败后，AI 输出如下结构化汇报，只讲关键点、不淹没在日志里：

```text
[Ontology Workshop 回归] 发现 2 个失败

├─ 失败 1: TestWidgetFieldStructure#everyWidgetConfigInterfaceMirrorsBackendFormFields
│   ├─ 类型: 契约真坏
│   ├─ 根因: 前端 config 接口 ObjectListWidgetConfig 新增字段 displayProperties，
│   │         但后端继承链上没有对应 @FormField
│   ├─ 影响: 该字段恒 undefined，组件静默失效（无任何报错）
│   ├─ 归属: tis-console/src/workshop/models/widgets/object-list.config.ts
│   └─ 建议: 后端补 @FormField，或前端删该幻影字段（需确认哪个是事实源）

└─ 失败 2: TestWorkshopConfigPlugins#rowEditorWireFormatKeysMatchFrontend
    ├─ 类型: 测试过期
    ├─ 根因: 前端 TuplesPropertyType 的 token 从 "interfaceInputRows" 改成 "inputRows"，
    │         测试里登记的期望值未同步
    ├─ 影响: 仅测试登记过期，产品本身无 bug
    ├─ 归属: plugins/.../workshop/TestWorkshopConfigPlugins.java
    └─ 建议: 更新测试里的前端 token 期望值
```

### 汇报铁律

1. **只报失败**：全绿时一句话「本次回归通过，N 个测试类全绿」，不逐条列。
2. **给类型 + 根因 + 归属 + 建议**，缺一不可；「类型」决定了开发者从哪个方向看。
3. **无法定位时如实说**「定位不出，需要开发者提供上下文」，绝不编造根因。
4. **标注可复现命令**：每条失败附上 `mvn -pl tis-ontology-plugin -am test -Dtest=XxxTest` 供开发者本地复现。

## 4. 落地：固化成 Claude Code Skill

把这个闭环固化成 skill，让「跑测试 → 分析 → 汇报」一条命令触发：

**落点**：`.claude/skills/ontology-workshop-test/SKILL.md`

skill 执行分三段（与闭环前三阶段一一对应）：

1. **执行段**——运行命令：
   - 后端契约测试：`mvn -pl tis-ontology-plugin -am test`（工作目录 `plugins`）
   - 前端 AOT：`npm run build`（工作目录 `tis-console`）
2. **分析段**——若失败：读日志 → 定位测试类 → 读登记清单与产品代码 → 按 §2 决策树归类。
3. **汇报段**——按 §3 模板输出结构化报告，附可复现命令。

### skill 的输入约定

- 开发者说「跑回归」→ 全量：后端 + 前端。
- 开发者说「跑 XxxTest」→ 单类：只跑指定测试，用于修复后的快速验证。
- 开发者说「回归 X」→ 只重跑上一轮失败的测试类（回归的最小闭环）。

## 5. 与 CI 的关系（兜底，不是主循环）

- **本地 skill 闭环是主循环**：人工在环，AI 分析 + 汇报，开发者修复，节奏快、反馈准。
- **CI 是兜底**：`ontology-workshop-test.yml` 在 push/PR 时全量跑，防「本地忘了跑」。
  CI 失败时仍回到本地闭环处理（拉下来 → 跑 → 分析 → 修复 → 回归）。
- CI 不追求「AI 自动修」——无人值守的自动改代码风险高，分析汇报在本地闭环里做更有上下文。

---

## 6. 交付节奏（如何「持续向用户交付可靠产品」）

```
每次改动 → 本地跑回归 → 全绿才提交
     │
     ├─ 失败 → AI 分析 → 汇报 → 开发者修复 → 重跑 → 转绿
     │
     ▼
push/PR → CI 全量跑 → 绿 → 可发布
```

配套纪律：

1. **每踩一个新坑 → 先补一条契约测试（钉住），再修产品代码**。这样「坑」从一次性的 bug 变成
   永久防回退的哨兵，测试资产随时间单调递增。
2. **契约清单（`contracts.md`）随测试同步更新**：`WorkshopContractInventoryTest` 保证清单不漂移。
3. **回归是增量的**：修复后只重跑失败类，确认转绿；周期性地（如发版前）跑全量。
