## 5.2 表结构定义

### 5.2.1 tis_flink_job_status（Flink Job 状态主表）

存储每个 DataX Pipeline 对应的 Flink Job 的运行状态。

```sql
CREATE TABLE `tis_flink_job_status` (
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `datax_name` VARCHAR(255) NOT NULL COMMENT 'DataX Pipeline 名称（唯一标识）',
  `job_id` VARCHAR(64) DEFAULT NULL COMMENT '当前 Flink JobID（16进制字符串）',
  `state` VARCHAR(32) NOT NULL DEFAULT 'CREATED' COMMENT '当前状态：CREATED/DEPLOYING/RUNNING/STOPPED/CANCELED/LOST/FAILED/RESTARTING/TERMINATED/RESTORE_FAILED/DEP_FAILED',
  `cluster_address` VARCHAR(255) DEFAULT NULL COMMENT 'Flink JobManager 地址',
  `tracking` TINYINT NOT NULL DEFAULT 0 COMMENT '是否正在跟踪：0-否, 1-是',
  `restart_count` INT NOT NULL DEFAULT 0 COMMENT '已自动重启次数',
  `max_restarts` INT NOT NULL DEFAULT 3 COMMENT '最大自动重启次数（任务级配置）',
  `auto_restore_enabled` TINYINT NOT NULL DEFAULT 1 COMMENT '是否启用自动恢复：0-否, 1-是',
  `last_restore_time` TIMESTAMP NULL DEFAULT NULL COMMENT '最后一次自动恢复时间',
  `last_seen_time` TIMESTAMP NULL DEFAULT NULL COMMENT '最后一次在集群中观察到该 Job 的时间',
  `create_time` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '记录创建时间',
  `update_time` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '记录更新时间',
  
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_datax_name` (`datax_name`),
  KEY `idx_state` (`state`),
  KEY `idx_tracking` (`tracking`),
  KEY `idx_state_tracking` (`state`, `tracking`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Flink Job 状态表';
```

#### 字段详细说明

| 字段名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `id` | BIGINT | AUTO_INCREMENT | 主键，自增 |
| `datax_name` | VARCHAR(255) | NOT NULL | DataX Pipeline 名称，如 `order_sync`。作为业务唯一键 |
| `job_id` | VARCHAR(64) | NULL | 当前 Flink JobID。集群重启后会变化，每次恢复后更新 |
| `state` | VARCHAR(32) | 'CREATED' | 状态枚举，见下方状态定义 |
| `cluster_address` | VARCHAR(255) | NULL | JobManager REST 地址，如 `http://localhost:8081`。缓存以减少配置查询 |
| `tracking` | TINYINT | 0 | Console 启动时加载 `tracking=1` 的记录到监控队列 |
| `restart_count` | INT | 0 | 当前生命周期内的自动重启次数。手动启动后重置为 0 |
| `max_restarts` | INT | 3 | 任务级配置，可覆盖全局默认值 |
| `auto_restore_enabled` | TINYINT | 1 | 任务级开关，允许对特定任务关闭自动恢复 |
| `last_restore_time` | TIMESTAMP | NULL | 用于控制恢复间隔，防止过于频繁的重试 |
| `last_seen_time` | TIMESTAMP | NULL | 用于判断失联时长 |
| `create_time` | TIMESTAMP | CURRENT_TIMESTAMP | 记录首次创建时间 |
| `update_time` | TIMESTAMP | ON UPDATE | 任何字段变更时自动更新 |

#### 状态枚举值

| 状态值 | 含义 | 是否终态 | tracking |
|--------|------|---------|----------|
| `CREATED` | 任务已创建，尚未部署 | 否 | 0 |
| `DEPLOYING` | 正在向 Flink 集群提交 | 否 | 1 |
| `RUNNING` | 正常运行中 | 否 | 1 |
| `STOPPED` | 用户手动停止（带 Savepoint） | ✅ 是 | 0 |
| `CANCELED` | 用户手动取消 | ✅ 是 | 0 |
| `LOST` | 集群失联，Job 不可达 | 否 | 1 |
| `FAILED` | 作业执行失败 | 否 | 1 |
| `RESTARTING` | 正在自动恢复过程中 | 否 | 1 |
| `TERMINATED` | 恢复次数耗尽或禁用自动恢复 | ✅ 是 | 0 |
| `RESTORE_FAILED` | 自动恢复尝试失败 | 否 | 0 |
| `DEP_FAILED` | 部署失败 | 否 | 0 |
| `MAPPING` | 手动映射已有 Job 中 | 否 | 1 |

### 5.2.2 tis_flink_restore_point（恢复点表）

存储每个 DataX Pipeline 的可用 Savepoint/Checkpoint 路径。

```sql
CREATE TABLE `tis_flink_restore_point` (
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `datax_name` VARCHAR(255) NOT NULL COMMENT 'DataX Pipeline 名称',
  `checkpoint_id` VARCHAR(64) DEFAULT NULL COMMENT 'Checkpoint/Savepoint ID',
  `path` VARCHAR(1024) NOT NULL COMMENT '恢复点存储路径（HDFS/S3 等）',
  `type` VARCHAR(16) NOT NULL DEFAULT 'CHECKPOINT' COMMENT '类型：SAVEPOINT / CHECKPOINT',
  `latest` TINYINT NOT NULL DEFAULT 0 COMMENT '是否是最新可用：0-否, 1-是。每个 datax_name 最多一条 latest=1',
  `trigger_time` TIMESTAMP NOT NULL COMMENT '该恢复点的触发时间',
  `create_time` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '记录创建时间',
  
  PRIMARY KEY (`id`),
  KEY `idx_datax_name` (`datax_name`),
  KEY `idx_datax_latest` (`datax_name`, `latest`),
  KEY `idx_trigger_time` (`datax_name`, `trigger_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Flink 恢复点表';
```

#### 字段详细说明

| 字段名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `id` | BIGINT | AUTO_INCREMENT | 主键 |
| `datax_name` | VARCHAR(255) | NOT NULL | 关联的 DataX Pipeline |
| `checkpoint_id` | VARCHAR(64) | NULL | Flink Checkpoint ID，如 `chk-12345` |
| `path` | VARCHAR(1024) | NOT NULL | 恢复点完整路径。提交时作为 `-s` 参数 |
| `type` | VARCHAR(16) | 'CHECKPOINT' | `SAVEPOINT`（手动触发）或 `CHECKPOINT`（自动触发）|
| `latest` | TINYINT | 0 | 标记最新可用恢复点，自动恢复时优先选择。更新时先清零旧记录再标记新记录 |
| `trigger_time` | TIMESTAMP | NOT NULL | 恢复点创建时间，用于排序和选择 |
| `create_time` | TIMESTAMP | CURRENT_TIMESTAMP | 记录写入时间 |

#### 关于 `latest` 字段的设计

采用"先清零再标记"策略而非使用 `MAX(trigger_time)` 查询，原因：
1. **查询性能**：直接 `WHERE latest=1` 比 `ORDER BY trigger_time DESC LIMIT 1` 更快
2. **数据一致性**：并发标记时更容易控制（通过事务）
3. **兼容性**：某些历史恢复点可能已被手动删除但记录仍在，`latest` 显式标记有效记录

更新 `latest` 的伪代码：

```sql
-- 在同一个事务中执行
BEGIN;
UPDATE tis_flink_restore_point SET latest = 0 WHERE datax_name = ?;
UPDATE tis_flink_restore_point SET latest = 1 
WHERE datax_name = ? ORDER BY trigger_time DESC LIMIT 1;
COMMIT;
```

### 5.2.3 tis_flink_restore_history（恢复历史表）

记录每次自动/手动恢复操作的审计日志。

```sql
CREATE TABLE `tis_flink_restore_history` (
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `datax_name` VARCHAR(255) NOT NULL COMMENT 'DataX Pipeline 名称',
  `old_job_id` VARCHAR(64) DEFAULT NULL COMMENT '恢复前的旧 JobID',
  `new_job_id` VARCHAR(64) DEFAULT NULL COMMENT '恢复后的新 JobID（成功时）',
  `restore_point_path` VARCHAR(1024) DEFAULT NULL COMMENT '使用的恢复点路径',
  `restore_mode` VARCHAR(16) DEFAULT 'CLAIM' COMMENT '恢复模式：CLAIM / NO_CLAIM',
  `trigger_type` VARCHAR(16) NOT NULL DEFAULT 'AUTO' COMMENT '触发类型：AUTO（自动）/ MANUAL（手动）/ FAILOVER（Checkpoint失败触发）',
  `success` TINYINT NOT NULL DEFAULT 0 COMMENT '是否成功：0-否, 1-是',
  `error_msg` TEXT DEFAULT NULL COMMENT '失败时的错误信息',
  `duration_ms` BIGINT DEFAULT NULL COMMENT '恢复操作耗时（毫秒）',
  `create_time` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '记录创建时间',
  
  PRIMARY KEY (`id`),
  KEY `idx_datax_name` (`datax_name`),
  KEY `idx_create_time` (`create_time`),
  KEY `idx_datax_time` (`datax_name`, `create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Flink 恢复历史表';
```

#### 字段详细说明

| 字段名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `id` | BIGINT | AUTO_INCREMENT | 主键 |
| `datax_name` | VARCHAR(255) | NOT NULL | 关联的 DataX Pipeline |
| `old_job_id` | VARCHAR(64) | NULL | 恢复前的 JobID，用于追溯 |
| `new_job_id` | VARCHAR(64) | NULL | 恢复成功后的新 JobID |
| `restore_point_path` | VARCHAR(1024) | NULL | 实际使用的恢复点路径 |
| `restore_mode` | VARCHAR(16) | 'CLAIM' | Flink 恢复模式 |
| `trigger_type` | VARCHAR(16) | 'AUTO' | 触发类型区分 |
| `success` | TINYINT | 0 | 操作结果 |
| `error_msg` | TEXT | NULL | 失败原因，便于排查 |
| `duration_ms` | BIGINT | NULL | 操作耗时，用于性能分析 |
| `create_time` | TIMESTAMP | CURRENT_TIMESTAMP | 操作时间 |

#### trigger_type 枚举

| 值 | 说明 |
|----|------|
| `AUTO` | Watcher 检测到 LOST/FAILED 后自动触发 |
| `MANUAL` | 用户手动点击"重新部署"或"认领 Job" |
| `FAILOVER` | Checkpoint 连续失败触发的 Failover |
| `UPGRADE` | 版本升级/配置变更后的计划内重启 |

## 5.3 索引设计说明

### 5.3.1 查询场景分析

| 查询场景 | WHERE 条件 | 使用索引 |
|---------|-----------|---------|
| Console 启动加载监控列表 | `tracking = 1` | `idx_tracking` |
| Watcher 查询指定任务状态 | `datax_name = ?` | `uk_datax_name`（唯一索引）|
| 获取所有 LOST 任务 | `state = 'LOST'` | `idx_state` |
| 获取需要自动恢复的任务 | `state IN ('LOST', 'FAILED') AND tracking = 1` | `idx_state_tracking` |
| 获取最新恢复点 | `datax_name = ? AND latest = 1` | `idx_datax_latest` |
| 查询恢复历史 | `datax_name = ? ORDER BY create_time DESC` | `idx_datax_time` |

### 5.3.2 索引优化建议

```sql
-- 对于大规模部署（上千个 Pipeline），可考虑分区
-- 按 datax_name 哈希分区或按 create_time 范围分区

-- 定期清理历史恢复点（保留最近 30 天的非 latest 记录）
DELETE FROM tis_flink_restore_point 
WHERE latest = 0 
  AND trigger_time < DATE_SUB(NOW(), INTERVAL 30 DAY);

-- 定期归档恢复历史（保留最近 90 天）
DELETE FROM tis_flink_restore_history 
WHERE create_time < DATE_SUB(NOW(), INTERVAL 90 DAY);
```

## 5.4 与现有表的关联

### 5.4.1 与 application 表的关联（可选）

如果 TIS 已有 `application` 或类似表管理 DataX Pipeline，建议通过 `datax_name` 做逻辑关联，而非外键约束（保持灵活性）。

```sql
-- 查询示例：获取所有运行中且启用了自动恢复的任务
SELECT 
  a.app_name,
  a.creator,
  s.job_id,
  s.state,
  s.restart_count,
  s.last_seen_time
FROM application a
LEFT JOIN tis_flink_job_status s ON a.app_name = s.datax_name
WHERE s.tracking = 1
ORDER BY s.last_seen_time ASC;
```

### 5.4.2 与现有 incr_job 本地文件的映射

```

    │ datax_name 从目录名解析
```

## 5.5 数据迁移方案

### 5.5.1 首次上线迁移

对于已有部署的 TIS 环境，需要一次性迁移本地文件状态到数据库：

```java
@Component
public class FlinkStatusMigrationTask implements CommandLineRunner {

    @Autowired
    private FlinkJobStatusStore jobStatusStore;

    @Override
    public void run(String... args) {
        // 检查数据库是否已有数据
        long count = jobStatusStore.count();
        if (count > 0) {
            logger.info("Database already has {} records, skip migration", count);
            return;
        }
        
        // 扫描所有 DataX Pipeline 目录
        File dataxDir = DataxProcessor.getDataXWorkDir(null);
        for (File pipelineDir : dataxDir.listFiles(File::isDirectory)) {
            String dataxName = pipelineDir.getName();
            File logFile = new File(pipelineDir, IFlinkIncrJobStatus.KEY_INCR_JOB_LOG);
            
            if (!logFile.exists()) {
                continue;
            }
            
            try {
                // 解析本地文件
                IFlinkIncrJobStatus fileStatus = FlinkIncrJobStatus.load(dataxName);
                
                // 写入数据库
                JobStatus dbStatus = new JobStatus();
                dbStatus.setDataxName(dataxName);
                dbStatus.setJobId(fileStatus.getLaunchJobID().toHexString());
                dbStatus.setState(JobState.RUNNING); // 假设运行中，后续 Watcher 会修正
                dbStatus.setTracking(true);
                dbStatus.setRestartCount(0);
                dbStatus.setMaxRestarts(3);
                dbStatus.setAutoRestoreEnabled(true);
                
                jobStatusStore.save(dbStatus);
                
                // 迁移 savepoint 记录
                List<SavePointMsg> savepoints = fileStatus.getSavePointPaths();
                if (savepoints != null) {
                    for (SavePointMsg sp : savepoints) {
                        RestorePoint rp = RestorePoint.builder()
                            .dataxName(dataxName)
                            .path(sp.getPath())
                            .type(RestorePointType.SAVEPOINT)
                            .triggerTime(new Date(sp.getCreateTime()))
                            .build();
                        jobStatusStore.saveRestorePoint(rp);
                    }
                    jobStatusStore.markLatestRestorePoint(dataxName);
                }
                
                logger.info("Migrated job status for: {}", dataxName);
                
            } catch (Exception e) {
                logger.error("Failed to migrate job status for: {}", dataxName, e);
            }
        }
    }
}
```

### 5.5.2 回滚方案

如果数据库方案出现问题，可快速回滚到纯文件方案：

```properties
# 回滚配置：关闭数据库存储，仅使用文件
flink.job.store.type=file
flink.job.restore.enabled=false
```

回滚后：
1. `FlinkJobRestoreManager` 停止自动恢复和数据库写入
2. `FlinkIncrJobStatus` 继续正常工作（文件机制未改动）
3. 用户回到手动管理模式

## 5.6 容量估算

### 5.6.1 存储估算

假设 TIS 管理 **500 个** Flink Job：

| 表 | 单条大小 | 数量 | 总大小 |
|----|---------|------|--------|
| `tis_flink_job_status` | ~500B | 500 | ~250KB |
| `tis_flink_restore_point` | ~2KB | 500 × 20（历史） | ~20MB |
| `tis_flink_restore_history` | ~3KB | 500 × 10（每月） | ~15MB/月 |

**结论**：数据量很小，不会对数据库造成压力。

### 5.6.2 QPS 估算

| 操作 | 频率 | QPS |
|------|------|-----|
| Watcher 查询状态 | 每 10 秒 × 500 Job | ~50 QPS |
| 状态更新 | 状态变化时 | < 1 QPS |
| Checkpoint 收集 | 每 30 秒 × 500 Job | ~17 QPS |

**结论**：数据库负载极低，无需特殊优化。
