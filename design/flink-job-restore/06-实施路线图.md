# 实施路线图

## 6.1 阶段划分

整个实施分为 **4 个阶段**，预计总工期 **4-6 周**（含测试）。

```
Phase 1: 基础设施（1 周）
    │
    ├── 数据库表创建
    ├── FlinkJobStatusStore 接口 + 实现
    └── 与现有 FlinkIncrJobStatus 的双写集成
    │
    ▼
Phase 2: 核心恢复逻辑（1.5 周）
    │
    ├── FlinkJobRestoreManager 开发
    ├── RestoreStrategy 策略实现
    ├── JobIdMapper 实现
    └── Watcher 轮询机制
    │
    ▼
Phase 3: 恢复点管理（1 周）
    │
    ├── CheckpointCollector 开发
    ├── Savepoint 自动落库
    └── 恢复点选择策略
    │
    ▼
Phase 4: 集成测试与优化（1.5 周）
    │
    ├── CoreAction 新增接口
    ├── 前端 UI 适配
    ├── 集成测试
    └── 性能优化与监控
```

### 端到端测试方案

#### 测试环境准备

```bash
# 1. 部署测试用的 Flink Standalone 集群
$FLINK_HOME/bin/start-cluster.sh

# 2. 启动 TIS Console（连接测试数据库）
mvn spring-boot:run -Dspring.profiles.active=test

# 3. 部署一个测试用的 DataX Pipeline Flink Job
# 通过 TIS UI 或 API 部署
```

#### 测试用例

```java
@Test
public void testAutoRestoreAfterClusterRestart() throws Exception {
    // 1. 部署一个 Flink Job
    String dataxName = "test_order_sync";
    JobID firstJobId = deployJob(dataxName);
    
    // 2. 等待 Job 进入 RUNNING 状态
    await().atMost(60, SECONDS).until(
        () -> getJobState(dataxName) == JobState.RUNNING
    );
    
    // 3. 模拟 Flink 集群重启（停止后再启动）
    stopFlinkCluster();
    Thread.sleep(5000);  // 等待集群完全停止
    startFlinkCluster();
    
    // 4. 验证 TIS 检测到 LOST
    await().atMost(30, SECONDS).until(
        () -> getJobState(dataxName) == JobState.LOST
    );
    
    // 5. 等待自动恢复完成
    await().atMost(120, SECONDS).until(
        () -> getJobState(dataxName) == JobState.RUNNING
    );
    
    // 6. 验证 JobID 已更新
    JobStatus status = jobStatusStore.findByDataxName(dataxName);
    assertNotNull(status);
    assertNotEquals(firstJobId.toHexString(), status.getJobId());
    
    // 7. 验证恢复历史有记录
    List<RestoreHistory> history = getRestoreHistory(dataxName);
    assertFalse(history.isEmpty());
    assertTrue(history.get(0).isSuccess());
}
```

#### 故障注入测试

| 故障类型 | 注入方法 | 期望行为 |
|---------|---------|---------|
| JM 网络断开 | iptables 屏蔽 8081 端口 | 标记 LOST，尝试恢复 |
| Savepoint 删除 | hdfs rm -rf | 恢复失败，进入 RESTORE_FAILED |
| 连续失败 | 模拟 Savepoint 路径不存在 3 次 | 达到 maxRestarts 后停止 |
| 数据库断开 | 停止 MySQL | 降级到文件存储，告警 |

## 6.7 验收标准

### 功能验收

| 验收项 | 标准 |
|--------|------|
| 自动恢复成功率 | >= 95%（在 Savepoint/Checkpoint 可用的情况下）|
| 状态检测延迟 | LOST 检测延迟 <= 轮询间隔 × 阈值 + 10s |
| 恢复操作延迟 | 从 LOST 到 RUNNING <= 60s（含集群启动时间）|
| 数据一致性 | 数据库状态与本地文件状态最终一致 |
| 手动 Mapping | 输入有效 JobID 后 5s 内完成绑定 |

### 非功能验收

| 验收项 | 标准 |
|--------|------|
| Console 启动时间 | 增加 < 5s（加载 500 个 tracking job）|
| Watcher 资源占用 | CPU < 5%, 内存 < 100MB |
| 数据库负载 | QPS < 100, 无慢查询 |
| 兼容性 | 关闭自动恢复后，与原有行为 100% 一致 |

## 6.8 后续优化方向

### 短期（1-2 个月）

1. **恢复模式智能选择**：根据 Checkpoint 大小和存储类型自动推荐 `CLAIM` 或 `NO_CLAIM`
2. **批量恢复**：集群大面积故障时，支持批量并行恢复多个 Job
3. **恢复通知**：恢复成功/失败后发送钉钉/企业微信/邮件通知

### 中期（3-6 个月）

1. **Kubernetes 模式增强**：监听 K8s Event，更快速地感知 Pod 变化
2. **跨集群迁移**：支持将 Job 从一个 Flink 集群迁移到另一个集群
3. **状态预检**：恢复前检查 Savepoint 与当前代码版本的兼容性

### 长期（6 个月以上）

1. **自愈闭环**：结合告警系统自动判断是短暂网络抖动还是真实故障，减少误恢复
2. **冷热分离**：长期不使用的恢复点归档到对象存储
3. **多版本管理**：支持按代码版本管理 Savepoint，便于回滚到历史版本
