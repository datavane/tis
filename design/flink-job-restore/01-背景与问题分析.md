# 背景与问题分析

## 1.1 项目背景

TIS（Trigger Incremental Sync）是一个企业级数据集成服务平台，基于批（DataX）、流（Flink-CDC、Chunjun）一体化架构，为用户提供端到端的数据同步能力。在流式处理场景中，TIS 通过启动 Flink 增量任务（Incr Sync Channel）来实现实时数据同步。

当前 TIS 的 Flink 任务管理采用**本地文件状态持久化**机制，每个 DataX Pipeline 对应一个本地状态文件 `incrJob.log`，用于记录当前 JobID、Savepoint/Checkpoint 历史等关键信息。

## 1.2 问题描述

### 1.2.1 核心痛点

在实际生产环境中，Flink 集群端可能因为以下原因发生宕机或重启：

- 物理机/虚拟机故障
- Kubernetes Pod 被驱逐或重新调度
- Flink JobManager/TaskManager 进程崩溃
- 集群维护性重启
- 资源不足导致容器重启

**当 Flink 端重启后，会出现以下问题链：**

```
Flink 集群重启
    → JobID 发生变化（新集群或 HA 未保留）
    → TIS 端 incrJob.log 中记录的旧 JobID 失效
    → RestClusterClient.getJobStatus(oldJobId) 返回 NOT_FOUND / DISAPPEAR
    → TIS 无法通过旧 JobID 连接到新的 Flink Job
    → 用户必须手动：
        1. 在 TIS 中删除原 Flink 任务
        2. 重新创建相同的 Flink Job（从 Savepoint/Checkpoint 恢复）
```

### 1.2.2 用户体验影响

当前的操作流程对用户极不友好：

1. **操作繁琐**：需要删除旧任务、重新创建、手动选择恢复点
2. **状态不可见**：TIS 端只能看到任务"消失"，无法判断是 Flink 端重启还是任务真正失败
3. **恢复点选择困难**：用户需要手动决定从哪个 Savepoint/Checkpoint 恢复，容易出错
4. **缺乏自动化**：没有自动重试、自动恢复机制，依赖人工介入
5. **监控滞后**：`FlinkJobsMonitor` 只能做到状态变化告警，无法自动修复

### 1.2.3 技术根源

| 根源 | 说明 |
|------|------|
| **状态存储方式局限** | JobID 保存在本地文件 `incrJob.log`，可靠性低，不利于集群共享 |
| **缺乏主动轮询恢复** | TIS 被动查询状态，发现失联后没有后续自动恢复动作 |
| **Savepoint 管理分散** | Savepoint/Checkpoint 路径散落在本地文件中，没有集中管理和自动选择机制 |
| **无重启策略** | 没有最大重启次数、恢复模式等策略配置 |

## 1.3 目标场景定义

### 1.3.1 场景一：Flink 集群内 HA 恢复

```
前提：Flink 集群配置了 HA（ZooKeeper / Kubernetes HA）
触发：JobManager 进程崩溃，由 HA 机制自动选举新 JM
结果：原 Job 在新 JM 上恢复，JobID 保留
TIS 期望行为：自动重新连接到恢复的 Job
```

### 1.3.2 场景二：Flink 集群完全重启

```
前提：整个 Flink 集群停止后重新启动（或迁移到新集群）
触发：集群维护、节点故障迁移、K8s StatefulSet 重建
结果：原 Job 不存在，JobID 必然变化，但 Savepoint/Checkpoint 文件可能保留
TIS 期望行为：
    1. 检测到旧 Job 不可达
    2. 自动获取最新的可用恢复点（Savepoint/Checkpoint）
    3. 自动重新提交任务（带上恢复点）
    4. 更新 JobID 跟踪信息
```

### 1.3.3 场景三：TIS Console 重启

```
前提：TIS Console 服务重启
触发：版本升级、配置更新、进程重启
结果：内存中的状态丢失
TIS 期望行为：
    1. 启动后自动从持久化存储恢复跟踪列表
    2. 继续监控之前正在运行的 Flink Job
```

## 1.4 设计目标

基于以上分析，本次设计的目标如下：

1. **自动恢复**：Flink 集群重启或 Job 失联后，TIS 能够自动检测到并尝试恢复任务
2. **状态持久化**：将 Flink Job 的关键状态从本地文件迁移到数据库，提升可靠性和共享能力
3. **恢复点自动管理**：自动收集和选择最新的可用 Savepoint/Checkpoint 作为恢复点
4. **可配置策略**：支持最大重启次数、恢复模式、自动恢复开关等策略配置
5. **兼容现有**：尽可能兼容当前的 `incrJob.log` 机制，降低迁移成本
6. **手动兜底**：提供"认领运行中 Job"的手动机制，覆盖自动机制无法处理的场景
