# 总体设计方案

## 3.1 设计原则

基于对 TIS 现状和 StreamPark 机制的分析，本次设计遵循以下原则：

1. **渐进式演进**：优先解决核心痛点（自动恢复），再逐步完善基础设施（状态持久化）
2. **向后兼容**：保留现有 `incrJob.log` 机制，新增数据库层为可选增强
3. **可配置化**：自动恢复行为（开关、次数、间隔）均通过配置控制
4. **最小侵入**：尽量复用现有代码（`FlinkTaskNodeController`、`CoreAction` 等）
5. **高可观测**：增加详细的日志、指标和状态流转记录，便于排查

## 3.2 方案选型

提供三种方案，由轻到重，适应不同的实施节奏：

### 方案对比

| 维度 | 方案 A（轻量） | 方案 B（标准） | 方案 C（完整） |
|------|--------------|--------------|--------------|
| **状态存储** | 本地文件 + 数据库双写 | 数据库为主，文件兼容 | 纯数据库 |
| **自动恢复** | ✅ 基于 Watcher 自动重投 | ✅ 更完善的策略控制 | ✅ 全自动 + 智能恢复点选择 |
| **Checkpoint 自动收集** | ❌ 手动触发 | ✅ 定时收集 | ✅ 实时事件驱动 |
| **手动 Mapping** | ✅ 简单实现 | ✅ 完整实现 | ✅ 完整实现 |
| **恢复模式** | ❌ 默认 | ✅ 可配置 | ✅ 可配置 + 自动推荐 |
| **改动量** | 小 | 中 | 大 |
| **实施周期** | 1-2 周 | 3-4 周 | 6-8 周 |

### 推荐方案：方案 B（标准方案）

方案 B 在改动量和收益之间取得最佳平衡：
- 引入数据库状态表，解决状态持久化和共享问题
- 实现自动恢复核心逻辑，解决用户核心痛点
- 自动收集 Checkpoint，确保恢复点可用
- 保留本地文件兼容层，平滑过渡

## 3.4 核心组件职责

### 3.4.1 FlinkJobRestoreManager（新增）

**职责**：统一协调 Flink Job 的故障检测、恢复决策和执行

**位置**：建议放在 `tis-console` 模块

```
FlinkJobRestoreManager
├── RestoreStrategy（恢复策略接口）
│   ├── AutoRestartStrategy（自动重启策略）
│   └── ManualRestoreStrategy（手动恢复策略）
├── JobIdMapper（JobID 映射器）
│   ├── 按 JobID 匹配
│   └── 按 JobName 匹配（兜底）
└── CheckpointCollector（恢复点收集器）
    ├── 定时轮询 Flink REST API
    └── 持久化到数据库/文件
```

### 3.4.2 FlinkJobStatusStore（新增）

**职责**：提供 Flink Job 状态的持久化存储抽象，屏蔽底层是文件还是数据库

**设计模式**：Repository 模式 + 适配器模式

```
FlinkJobStatusStore（接口）
├── FileSystemJobStatusStore（现有逻辑封装）
│   └── 读写 incrJob.log
└── DatabaseJobStatusStore（新增）
    └── 读写 tis_flink_job_status
```

### 3.4.3 CheckpointCollector（新增）

**职责**：定时收集 Flink Job 的 Checkpoint/Savepoint 信息，维护最新的可用恢复点

**触发方式**：
- 定时任务：每 30 秒扫描一次 `tracking=1` 的作业
- 事件驱动：作业状态变化时主动收集

**关键状态说明**：

| 状态 | 说明 | 是否终态 |
|------|------|---------|
| `CREATED` | 任务已创建，尚未部署 | 否 |
| `DEPLOYING` | 正在向 Flink 集群提交 | 否 |
| `RUNNING` | 正在运行，正常状态 | 否 |
| `STOPPED` | 用户手动停止（带 Savepoint） | ✅ 是 |
| `CANCELED` | 用户手动取消 | ✅ 是 |
| `LOST` | 集群失联，无法通过 REST API 访问 | 否（可恢复） |
| `FAILED` | 作业执行失败 | 否（可自动恢复） |
| `DEP_FAILED` | 部署失败 | 否（可重试） |
| `RESTARTING` | 正在自动恢复中 | 否 |
| `TERMINATED` | 自动恢复次数耗尽或禁用自动恢复 | ✅ 是 |

## 3.7 与现有模块的集成点

### 3.7.1 与 CoreAction 的集成

现有 `CoreAction` 中的 Flink 操作方法保持不变，新增以下接口：

| 新增接口 | 作用 |
|---------|------|
| `doEnableAutoRestore` | 开启/关闭指定任务的自动恢复 |
| `doManualMapJob` | 手动认领一个运行中的 Flink Job |
| `doGetRestoreHistory` | 查询自动恢复历史记录 |

### 3.7.2 与 FlinkTaskNodeController 的集成

复用现有的提交、查询、控制逻辑：

- `FlinkTaskNodeController.getRCDeployment()` —— 用于 Watcher 查询状态
- `FlinkTaskNodeController.triggerSavePoint()` —— 用于停止时触发 Savepoint
- `FlinkTaskNodeController.relaunch()` —— 用于自动恢复时重新提交
- `FlinkTaskNodeController.restoreFromCheckpoint()` —— 用于从 Checkpoint 恢复

### 3.7.3 与 FlinkIncrJobStatus 的集成

保持 `FlinkIncrJobStatus` 的文件读写逻辑，增加数据库双写：

```java
// 伪代码示意
public void createNewJob(JobID jobId) {
    // 1. 保持原有逻辑：写入 incrJob.log
    super.createNewJob(jobId);
    
    // 2. 新增：同步写入数据库
    if (jobStatusStore != null) {
        jobStatusStore.save(JobStatus.builder()
            .dataxName(this.dataxName)
            .jobId(jobId.toHexString())
            .state(JobState.RUNNING)
            .tracking(true)
            .build());
    }
}
```

## 3.8 异常处理策略

### 3.8.1 自动恢复失败的处理

```
自动恢复时可能遇到的异常：

1. Savepoint 路径不存在或已删除
   → 尝试使用次新的 Savepoint/Checkpoint
   → 如果都不可用，标记为 RESTORE_FAILED，告警通知

2. Flink 集群不可达（网络故障）
   → 保持 LOST 状态，继续重试（按指数退避策略）
   → 最大重试次数后标记为 TERMINATED

3. 提交成功但 Job 立即失败
   → Watcher 检测到 FAILED，再次触发自动恢复
   → 受 restart_size 限制

4. 数据库写入失败
   → 降级到仅写本地文件，告警通知
   → 不阻塞主流程
```

### 3.8.2 降级策略

```
数据库不可用时的降级路径：

正常路径：FileSystemStore <-> DatabaseStore（双写）
          ↓
降级路径：仅 FileSystemStore（写文件，告警提示"数据库不可用"）
          ↓
最低路径：仅内存状态（Console 重启后丢失，需手动恢复）
```

## 3.9 配置项设计

```properties
# ========== Flink Job 自动恢复配置 ==========

# 是否启用自动恢复功能（全局开关）
flink.job.restore.enabled=true

# 自动恢复的最大重试次数（默认 3 次）
flink.job.restore.max-restarts=3

# 两次自动恢复之间的最小间隔（秒，默认 60）
flink.job.restore.min-interval-sec=60

# 首次自动恢复的延迟（秒，给集群启动留时间，默认 30）
flink.job.restore.initial-delay-sec=30

# 恢复模式：CLAIM（接管状态文件）/ NO_CLAIM（复制状态）
flink.job.restore.mode=CLAIM

# 是否允许忽略未声明的状态（默认 true）
flink.job.restore.allow-non-restored-state=true

# ========== Checkpoint 收集配置 ==========

# 是否自动收集 Checkpoint 作为恢复点
checkpoint.collect.enabled=true

# Checkpoint 收集间隔（秒，默认 30）
checkpoint.collect.interval-sec=30

# 保留的 Checkpoint 历史数量（默认 10）
checkpoint.collect.max-history=10

# ========== Watcher 配置 ==========

# 状态监控轮询间隔（秒，默认 10）
flink.watcher.poll-interval-sec=10

# 失联判定阈值（连续失败次数，默认 3）
flink.watcher.lost-threshold=3
```

## 3.10 安全与权限考虑

1. **自动恢复权限**：自动恢复操作应使用系统级 Token，避免依赖用户会话
2. **并发控制**：同一任务的自动恢复应加分布式锁，防止并发重投
3. **审计日志**：所有自动恢复操作记录审计日志（who/what/when/result）
4. **资源保护**：自动恢复次数限制防止资源耗尽
